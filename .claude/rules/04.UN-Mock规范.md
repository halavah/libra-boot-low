## 三、幂等策略（强制）

### 3.1 业务表：`TRUNCATE + INSERT`

```sql
-- 幂等：每次重置后全量插入
TRUNCATE TABLE {prefix}_product;
INSERT INTO {prefix}_product (id, product_name, ...) VALUES
(3001, '商品A', ...),
(3002, '商品B', ...);
```

### 3.2 sys_user：`INSERT ... ON DUPLICATE KEY UPDATE`

**不删表、不重建**，仅追加测试账号：

```sql
INSERT INTO sys_user (user_id, login_name, ...)
VALUES (9003, 'zgh_test', ...)
ON DUPLICATE KEY UPDATE
  password = VALUES(password),
  name = VALUES(name);
```

### 3.3 禁止 DROP TABLE / CREATE TABLE

DDL 在 `server_exec.sql` 中统一管理，mock 文件只做 DML。

## 六、链路检查清单

每次新增或修改 mock 数据后，必须逐项验证：

1. **订单 → 台账**：每条已发货订单（status=4）在 `{prefix}_ledger` 中有对应记录
2. **订单 → 积分消费**：每条 status≥3 的订单在 `{prefix}_points_log` 中有 `SUB_EXCHANGE` 记录（审核通过时扣减）
3. **积分退回**：被驳回（status=5）的订单必须有 `ADD_REFUND` 记录
4. **同步状态**：至少 3 条 `sync_status=0` 的 `points_log`，供 Scheduler 测试
5. **分页数据**：zgh_test(9003) 的 `points_log` 至少 10 条，支持分页展示
6. **方案与商品**：`{prefix}_plan` 每条记录在 `{prefix}_plan_product` 中有至少 1 条关联

## 八、完整业务闭环数据要求

> **目标**：Mock 数据必须支撑从登录到积分同步的全链路业务闭环，
> 每个测试账号在各表中拥有足够记录满足分页展示测试（≥10 条）。

### 8.0 订单数据设计原则（2026-06-02 新增）

本次订单 mock 重构遵循以下设计原则，取代历史版"一人多单 + 部分消费"模式：

| 原则 | 定义 | 实现方式 |
|------|------|---------|
| **一人一单** | 每个测试账号每节日仅 1 条订单 | 按 user_id + holiday_id 唯一，避免历史版混乱 |
| **全额消费** | 订单 total_amount = 套餐 unit_price | 用户积分全额消费，不留余额 |
| **aid_ratio ≥ 0.30** | 助农商品金额占比 ≥ 30% | 每个商品组合方案确保 aid_total / total_amount ≥ 0.30 |
| **状态全覆盖** | 每个角色的订单覆盖全部可达状态 | 见 §8.3 状态矩阵 |

## 十、列对齐 DDL 规范（2026-06-02 新增）

### 10.1 强制要求

| 规则 | 说明 | 等级 |
|------|------|------|
| INSERT 列名必须是 DDL 中存在的列 | 禁止引用 DDL 中不存在的列 | 强制 |
| INSERT 列数 ≤ DDL 列数 | 允许省略有 DEFAULT 值的列，禁止多出列 | 强制 |
| 数据值数量 = INSERT 列名数量 | 每行 VALUES 的值必须与列名一一对应 | 强制 |
| 列顺序建议与 DDL 一致 | 减少维护成本，便于人工核对 | 建议 |

### 10.2 允许省略的列

以下列在 mock 数据中可以省略（由 MySQL 自动填充默认值）：

| 列类型 | 示例 | 默认值 | 省略条件 |
|--------|------|--------|---------|
| 审计字段 | `create_user`, `create_dept`, `update_user` | DEFAULT NULL | 测试数据不涉及数据权限过滤时 |
| 业务可选字段 | `person_id`, `image_url` | DEFAULT NULL | 该字段非当前测试场景关键路径时 |
| 标志字段 | `is_aid` | DEFAULT 0 | 测试非助农场景时 |

> **注意**：省略审计字段可能导致数据权限查询（如 `WHERE create_dept = ?`）查不到记录，
> 在测试数据权限前须补齐。

### 10.3 列一致性检查流程

每次修改 mock 文件后，执行以下检查：

```bash
# 1. 提取 DDL 列名
sed -n '/CREATE TABLE `表名`/,/)/p' server_exec.sql | grep '^  `' | awk -F'`' '{print $2}'

# 2. 提取 INSERT 列名
grep -A5 'INSERT INTO' server_mock_XX_表名.sql | grep '`'

# 3. 对比两者是否一致
diff <(ddl_cols) <(insert_cols)
```

## 十一、设计文档同步（仅结构变更触发）

> 适用范围：`01-design/` 下的 `database.md` 和 `model.md`

### 11.1 同步触发条件

| Mock 变更类型 | 是否触发 database.md/model.md 同步 |
|---------|--------------------|
| 因 DDL 结构变更（新增表/删除表/新增字段/删除字段/字段类型变更/表关系变更）导致 Mock 文件相应调整 | ✅ 触发同步 |
| 纯 Mock 数据值修复（修正错值、补充缺失记录、调整外键 ID 关联、status 状态值调整） | ❌ 不触发同步 |
| Mock INSERT 列对齐 DDL（仅顺序调整、无新增字段） | ❌ 不触发同步 |
| 新增 Mock 文件（`server_mock_XX_表名.sql`）对应一张全新业务表 | ✅ 触发同步 |

### 11.2 操作流程（结构变更场景）

当 Mock 文件因结构变更而调整时，**必须按以下顺序操作**：

1. 先在 `server_exec.sql` 中完成 DDL 结构变更
2. 同步更新 `01-design/database.md`（DDL 字段定义快照）
3. 同步更新 `01-design/model.md`（17 表字段索引/三层结构/业务流关联）
4. 然后才能调整对应的 `server_mock_XX_*.sql` 文件
5. 最后执行 `run_mock.sh 0 --yes` 验证

**禁止**：
- 先改 Mock 文件，后改 DDL（顺序颠倒会导致 Mock 与 DDL 不一致）
- 改了 Mock 不改设计文档（结构变更未同步违反冻结策略）
- 仅改 Mock 数据值却误触发设计文档同步（数据值变更不触发）

### 11.3 三文件联动检查清单

每次因结构变更调整 Mock 文件后，逐一核对：

```text
[ ] server_exec.sql — DDL 列定义（字段名、类型、默认值、注释）
[ ] server_enum.md — 枚举值文档（新增/变更的枚举取值）
[ ] server_mock_XX_*.sql — Mock INSERT 字段与 DDL 列完全匹配
[ ] 01-design/database.md — DDL 字段定义快照已同步
[ ] 01-design/model.md — 17 表字段索引/三层结构/业务流关联已同步
```
